Autonomous ML Research Agent · KuaiRand-Pure

An agent that writes its own recommender

Given a dataset and two metrics, it explores, writes code, trains, evaluates, reads its own training logs, diagnoses what went wrong, and tries again — with nobody watching. The submitted artifact is the agent. The model is just what it happened to produce.

What the number doesn't say

Validation-best was 0.6033, a +0.0017 lead. On test that became +0.0003 — roughly 20% transfer. The winning iteration added hour-of-day and recency features, which helped on the seven-day validation window and did not survive the ten-day test window that follows it. Ordinary validation overfitting, and the competition's own selection rule offers no protection against it: the thing you select on is the thing you overfit.

How it works

One append-only journal, and everything derived from it

logs/journal.jsonl is the spine. One entry per attempted iteration, and it serves three roles at once: the judge deliverable, the agent's own memory for its reflect step, and the sole source for every report. Nothing else stores run state. If a number isn't derivable from the journal, it isn't reported.

policy reflect over the journal → action + falsifiable hypothesis
codegen surgical SEARCH/REPLACE edit, or a rewrite if the approach changes
guards syntax, I/O contract, test-split leakage — all before execution
executor subprocess, hard timeout, never exec()
eval the organisers' own scorer, vendored unmodified
critic accept → git commit + patch + checkpoint · reject → revert
journal append → memory, reports, convergence

The workspace is its own git repository, so the commit graph is the search tree. An accepted iteration is a commit; a rejection is git checkout . && git clean -fd; backtracking is a branch from an earlier commit. The per-iteration diff deliverable is just git format-patch.

Two guards exist to protect us from ourselves rather than from the model. The test split's labels sit in the same local CSVs as validation, so "scored once" is enforced structurally: the loop has no code path to a test score, generated code is linted for test-split references before it runs, and the one-shot evaluation refuses to run twice. Separately, the unbiased random-exposure log spans the test window, so the harness slices it to the validation window before the agent ever sees it.

Innovation

What the agent worked out on its own

These are unedited hypotheses from the journal. None was prompted; each is the agent reading its own evidence.

"train_loss keeps falling every epoch while valid_primary peaks at epoch 4 and then degrades for 4 more — classic overfitting of the user_id × video_id embeddings, not underfitting." → raised L2 from 1e-6 to 1e-4 as a one-line edit. Accepted. This produced most of our gains.
"hourmin varies row-to-row even within a single user's impression list, so unlike user_id it isn't nulled out by within-user ranking." → independently derived the structural rule that anything constant within a user contributes exactly zero, then picked a feature that survives it.
"The previous iteration's code_error came from an implementation bug wiring DataFrames into data.load/encode/FM — not from a flawed idea." → separated a broken implementation from a wrong hypothesis, and kept the hypothesis.
"LightGBM categorical splits handle very high-cardinality ids poorly — each leaf isolates a handful of id combinations, unlike FM's learned latent factors." → diagnosed why its own tree model underperformed a factorization machine, and switched.
The finding

Match the metric's k, not the group size

The evaluator groups strictly by user. In the training split a user has a median of 31 impressions; in the evaluation splits, 4 to 5. So any listwise or pairwise ranker trained on whole users learns to order ~31-item lists and is then scored on ~5-item ones. Across fifteen runs, every listwise attempt the agent made — lambdarank, BPR, softmax — lost to a pointwise factorization machine. This is why.

A controlled experiment, identical model and features and seeds, varying only how training rows are chunked into groups:

The peak is sharp at exactly five, reproduced across eight seeds in two independent sets. The mechanism is the metric itself: it is nDCG@5. A training list of exactly five sits entirely inside the cutoff, so every position contributes gradient. At six or more, some positions fall outside it; at four, the list is shorter than the cutoff and carries less signal per group. The rule isn't "match the average group size" — it's match the metric's k, which predicts a sharp peak rather than a broad optimum, and the neighbours behaving differently is evidence for it rather than noise against it.

Honest scope: a chunk-5 lambdarank reaches 0.6013 against FM's 0.6016. It repairs the handicap; it doesn't win on its own. Blending it with a pointwise model reached ~0.603 — the same ceiling the agent had already found by a different route, which is itself evidence the ceiling is real.

Autonomy & robustness

Every failure, and what happened next

Robustness here is not a low failure count — it's what happens after one. All thirteen error events across all runs were journaled with the recovery taken, and every one recovered. Representative examples:

code_errorGenerated code raised. Workspace reverted, a debug iteration scheduled, which restored the accepted node and re-implemented the idea carefully.
timeoutPipeline exceeded the hard limit. Whole process group killed, partial stdout captured and fed back so the next attempt knew it had to be cheaper.
bad_llm_outputResponse truncated or unparseable. Named precisely — truncation and refusal both return HTTP 200 and would otherwise look like nonsense downstream.
llm_api_errorProvider unreachable. Journaled, and the policy returns a labelled FALLBACK proposal so the run continues and the hypothesis is honestly attributed to the harness, not the agent.

Sixteen runs were performed while the harness was debugged, and the best was submitted. Choosing the maximum of several runs is worth more than any single run is expected to score, so reports/run_history.md publishes the whole distribution rather than the number we chose: best 0.6033, median 0.6018, mean 0.5980 ± 0.0077, with 8 of 16 runs at or above baseline.

Most of that spread was our fault, not the agent's

Truncated code generation from a too-small output budget. A missing validation split that left the agent early-stopping on a memorisation-inflated internal holdout reading 0.95 against a true 0.60. API signatures documented by name but not by shape, so it wrote a wrapper that guessed argument order until one stopped throwing. A column the pipeline never joined. Each cost real iterations, and the agent only gets three after its best node. Runs on either side of a fix are not comparable samples of the same system.

Limitations

What we'd fix given more time

  • The critic is greedy. Accept-if-best is hill-climbing; it never keeps a neutral change that might unlock something two moves later. Tree search mitigates this — the policy can branch from any accepted commit — but there is no explicit exploration budget.
  • Journal-as-memory compresses crudely. The last eight iterations render in full and older ones collapse to a row. That holds for tens of iterations, not hundreds, and because the journal is the memory, any lossy scheme changes behaviour.
  • gpu_seconds is unmeasured. Token accounting is airtight — one call site, every call recorded including failures and retries. GPU attribution inside the subprocess is not. It reads zero because the path is genuinely CPU-only, but a torch escalation would need a real meter first.
  • Convergence punishes honesty about failure. A crash streak counts as no-improvement and can end a run at N=3. Defensible, but a judgement call rather than an organiser rule.
  • The validation→test gap is the binding constraint. Not our modelling. At ~20% transfer, pushing validation to 0.605 would buy roughly +0.0007 on test. We stopped optimising for that reason rather than from lack of ideas.
